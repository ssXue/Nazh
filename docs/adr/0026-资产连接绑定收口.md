# ADR-0026: 资产连接绑定收口

- **状态**: 已接受
- **日期**: 2026-05-23
- **决策者**: ssxue
- **关联**: ADR-0021, ADR-0024, ADR-0025, `docs/specs/2026-05-23-资产连接绑定收口.md`

## 背景

Nazh 已经把连接、设备、能力收敛到 DSL 资产体系：

- 连接资产：`dsl/connections/*.connection.yaml`
- 设备资产：`dsl/devices/*.device.yaml`
- 能力资产：`dsl/capabilities/*.capability.yaml`

ADR-0025 已决定连接资产只保存工程可审查的协议拓扑、治理策略和 secret 引用，运行态状态由 `ConnectionManager` 管理。ADR-0021 / ADR-0024 则把业务编排主路径推向 Device / Capability / Workflow，而不是直接操作协议节点。

但实际产品链路仍存在重复绑定问题。典型流程是：

```text
新建设备
  -> 新建连接
  -> 在连接中配置现场参数
  -> 在设备上绑定连接
  -> 在节点上再次绑定连接
  -> 部署
```

EtherCAT 场景最容易暴露这个问题：用户导入 ESI/ENI 后，需要新建 EtherCAT 总线连接、配置网卡和 DC 参数、把设备绑定到这条总线、再在 PDO 或设备信号节点上选择同一条连接。类似重复配置也存在于 Modbus、Serial、CAN、MQTT、HTTP/Bark 等协议。

这会带来几个长期问题：

- 用户需要在设备、连接、节点三层重复选择同一资源，操作链路长且容易出错。
- 设备绑定与节点绑定可能冲突，用户难以判断哪个连接真正生效。
- AI 编排需要理解底层连接 ID，而不是只围绕设备能力生成可审查的业务动作。
- 部署期若解析整个工作区的所有连接资产，无关坏连接可能阻塞当前工作流。
- 连接测试如果只出现在部署或首次运行时，错误发现太晚。

因此需要一个跨协议的绑定决策，明确连接、设备、能力、节点和部署各自承担什么责任。

## 决策

> 我们决定采用“设备绑定一次，高级业务节点继承连接，低层协议节点显式绑定”的资产连接模型。连接资产描述“怎么连”，设备资产描述“这台设备挂在哪条连接上”，能力和高级设备节点默认继承设备连接；只有协议调试/适配器节点直接暴露 `connection_id`。部署期只解析当前工作流实际引用的连接资产，资产页通过显式诊断动作做一次性探测，不在保存资产时建立持久连接。

具体规则：

1. **设备是业务绑定点**：业务设备在 `DeviceSpec.connection` 上绑定默认连接。该绑定是高级设备节点和能力调用的默认连接来源。
2. **高级节点继承连接**：`deviceSignalRead`、`deviceEventTrigger`、`capabilityCall` 和未来高级设备动作节点，不应要求普通用户重复填写 `connection_id`。UI 必须展示解析后的连接和来源。
3. **低层节点保留显式连接**：`modbusRead`、`serialTrigger`、`mqttClient`、`canRead`、`canWrite`、`ethercatPdoRead`、`ethercatPdoWrite`、HTTP/Bark 等协议调试或适配器节点，可以直接选择连接，但不作为 AI 编排和业务画布主路径。
4. **不猜默认连接**：缺少设备绑定、连接资产、secret 或环境覆盖时，编译/部署/运行必须 fail fast，并给出可定位错误。不得根据协议类型或“第一个可用连接”自动猜测。
5. **部署只解析引用连接**：部署前应从 `WorkflowGraph`、设备快照、能力快照和低层节点显式 `connection_id` 中收集实际引用的连接 ID，只解析这些连接资产。项目级全连接检查是独立诊断能力，不是普通部署硬前置。
6. **资产保存不持有连接**：保存连接资产或设备资产只做结构和安全校验，不建立持久硬件/网络会话。连接页和设备页可以提供显式“测试/诊断”动作，诊断使用一次性 probe 生命周期，结束后释放资源。
7. **连接来源可审计**：编译产物、UI 和部署审计应能表达连接解析来源，例如 `device.connection`、能力级覆盖或低层节点显式绑定。审计只记录脱敏摘要，不记录 secret。

## 可选方案

### 方案 A: 所有节点都直接选择连接

- 优势：实现最简单；与现有 `WorkflowNodeDefinition.connection_id` 和低层协议节点模型最兼容；节点运行时不需要额外解析设备资产。
- 劣势：用户需要在设备和节点上重复绑定；节点绑定和设备绑定可能冲突；AI 编排被迫关心底层连接 ID；连接资源会重新成为业务编排主语，违背 ADR-0021 的设备/能力优先方向。

### 方案 B: 设备绑定一次，高级节点继承连接

- 优势：用户心智清晰；连接配置和设备语义职责分离；AI 编排只需要选择设备、信号和能力；部署审计能解释连接来源；跨 Modbus、Serial、CAN、EtherCAT、MQTT 等协议都能统一。
- 劣势：需要补齐绑定解析、UI 可见性、部署引用收集和诊断 IPC；短期要调整已有节点设置面板和 copilot prompt。

### 方案 C: 连接完全由设备导入流程自动生成

- 优势：设备建模链路最短；用户导入说明书、ESI 或点表后可以直接得到设备和连接草稿。
- 劣势：多个设备共享同一总线或 broker 时会产生重复连接；连接治理、secret、本机覆盖、环境差异不是设备语义的一部分；长期会让 Device DSL 吞并连接资源池职责。

### 方案 D: 部署期自动猜测默认连接

- 优势：用户配置项最少；旧工作流在缺少绑定时可能“看起来能跑”。
- 劣势：违反运行时配置显式声明和 fail-fast 约束；错误不可解释；多连接同协议时容易选错现场资源；审计无法证明动作使用了用户确认过的连接。

## 后果

### 正面影响

- 普通业务链路从“设备 + 连接 + 节点重复配置”收敛为“设备绑定一次，节点引用设备语义”。
- AI 编排上下文更稳定：模型只需要基于已审查设备/能力生成 Workflow DSL 或高级节点，不需要猜测底层连接 ID。
- 连接资产继续保持资源层边界，`ConnectionManager` 继续只负责运行态治理、RAII 借出、共享会话和健康状态。
- 部署解析范围更小，无关坏连接不再阻塞当前工作流。
- 显式诊断动作能在资产阶段发现网卡、串口、host、secret、从站拓扑等问题，同时不污染运行态生命周期。

### 负面影响

- 前端需要调整节点设置 UI：高级设备节点显示继承连接，低层协议节点才直接编辑连接。
- 部署链路需要新增引用收集和按 ID 解析连接资产，不能简单加载全部连接资产。
- 需要在编译产物或部署审计中保存连接来源摘要，否则用户会看不到“隐式继承”的结果。
- 某些跨设备、跨通道能力需要设计高级覆盖入口，不能完全依赖设备默认连接。

### 风险

- **风险：隐藏连接选择后，用户不知道节点实际使用哪条连接。** 缓解：高级节点 UI 必须展示解析后的连接 ID、连接类型、来源和跳转入口；部署审计记录脱敏绑定摘要。
- **风险：能力级覆盖重新引入重复配置。** 缓解：覆盖只作为高级选项，默认继承设备连接；覆盖必须显式标记并进入审计。
- **风险：诊断 probe 污染部署期共享会话，尤其是 CAN/EtherCAT。** 缓解：诊断使用独立临时生命周期，结束后清理，不写入部署共享会话缓存。
- **风险：部署只解析引用连接后，项目级坏连接更晚被发现。** 缓解：提供“全连接检查”独立入口，连接页显示项目级健康结果，但普通部署不被无关连接阻塞。
- **风险：现有低层节点和历史画布仍依赖 `connection_id`。** 缓解：低层节点继续支持显式连接；主路径先收口 `deviceSignalRead` / `deviceEventTrigger` / `capabilityCall` 和 AI 编排，不做破坏性删除。

## 备注

- 详细产品链路、协议适配表、阶段计划和测试策略见 `docs/specs/2026-05-23-资产连接绑定收口.md`。
- 本 ADR 不替代 ADR-0025。ADR-0025 解决连接资产真值源问题；本 ADR 解决连接资产、设备资产、能力和节点之间的绑定责任问题。
- 本 ADR 不引入连接热切换。连接资产或设备绑定变化后，当前仍以重新部署作为生效路径。
- 实施时应同步更新 root `AGENTS.md` 的设计原则、`crates/dsl-core/AGENTS.md` 的 Device/Connection 修改 checklist，以及相关 UI / IPC / ts-rs 生成类型。
