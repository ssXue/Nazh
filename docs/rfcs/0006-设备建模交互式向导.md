# RFC-0006：设备建模 Copilot 接管

> **状态：** 讨论中
> **日期：** 2026-05-26
> **决策者：** ssXue
> **关联：** RFC-0004（三段式 DSL，Phase 1/2 已实施）、RFC-0005（AI 调用前移到前端）、ADR-0008（元数据与载荷分离）、ADR-0012（工作流变量）

## 摘要

用 copilot 对话**替换**当前所有设备建模 UI 入口。现有入口碎片化为四条独立路径——DeviceImportDrawer（粘贴文本 / 上传 PDF / EtherCAT ESI）、手动信号/告警表单编辑、能力生成按钮、copilot 设备搜索——用户需在不同 UI 间跳转且无法交叉利用。本 RFC 在 copilot 中新增三类工具（校验工具 3 个、资产读取工具 2 个、资产操作工具 8 个）+ 设备建模专家系统提示 + copilot 输入区文件附件 UI，使 copilot 成为设备建模的**唯一入口**，同时移除 DeviceImportDrawer 和 DeviceModelingPanel 的建模编辑能力。"资产"区域降级为只读设备浏览器。

## 动机

### 当前入口碎片化

用户完成一次完整设备建模需要跨越 **4 个独立 UI 区域**：

```
入口 1：DeviceImportDrawer（"接入设备" 按钮）
  ├─ 粘贴文本 → AI 一次性抽取 → 自动保存
  ├─ 上传 PDF → Rust 文本提取 → AI 抽取 → 自动保存
  └─ EtherCAT ESI → Rust 确定性解析 → 自动保存

入口 2：DeviceModelingPanel 详情（手动编辑）
  ├─ 信号表：逐行 inline form 添加/编辑/删除信号
  ├─ 告警表：逐行 inline form 添加/编辑/删除告警
  ├─ 连接绑定：下拉选择 connection
  └─ 字段编辑：EditableField patch model/manufacturer

入口 3：CapabilitiesTab（能力生成）
  └─ "生成" 按钮 → generate_capabilities_from_device_cmd → 逐条保存

入口 4：Copilot（设备查询 + 画布操作）
  ├─ search_devices / search_capabilities / read_asset_yaml（只读查询）
  └─ add_workflow_node(capabilityCall)（画布创建节点）
```

**问题**：

1. **信息遗漏无补救**：AI 抽取（入口 1）是单向的——说明书缺少寄存器地址时 AI 编造占位值或静默跳过。工业现场寄存器配错可能引发安全事故。没有追问机制。
2. **校验滞后**：`parse_device_yaml_validated` 是空壳。设备 YAML 的信号 ID 唯一性、量程合法性、协议一致性等语义约束完全没有校验，直到运行时才暴露。
3. **能力生成断崖**：`try_generate_capabilities_from_device()` 对 CAN / Modbus / EtherCAT 写信号直接报错，没有降级路径。
4. **四入口无联动**：从 AI 抽取（入口 1）到手动编辑（入口 2）到能力生成（入口 3）到画布使用（入口 4），每一步都是独立操作。AI 不知道后续步骤需要什么信息，手动编辑不知道 AI 之前跳过了什么。
5. **现有 copilot 只是旁观者**：copilot 能搜索设备和创建画布节点，但不能创建/编辑设备、不能校验、不能生成能力——它对设备建模没有任何写入能力。

### 目标

**copilot 成为设备建模的唯一入口**。用户在 copilot 对话中完成从"描述设备"到"校验信号"到"生成能力"到"保存资产"的全部流程。PDF / ESI 文件通过 copilot 输入区的文件附件按钮导入。现有建模 UI（DeviceImportDrawer、DeviceModelingPanel 的信号/告警编辑、CapabilitiesTab 的生成按钮）被移除。"资产"区域降级为只读设备浏览器，不再承载任何建模编辑逻辑。

具体目标：

- copilot 在多轮对话中追问关键缺失字段，**绝不为寄存器地址、量程、报警阈值编造数值**
- 设备 YAML 在建模过程中实时校验（结构 + 语义），错误在对话中即时暴露并修正
- 能力生成从"成功或报错"二分法，改为"自动生成 + AI 辅助手动建模"的渐进路径
- copilot 可直接创建/修改/删除设备资产、生成能力、绑定连接——唯一入口，无并行路径
- 不引入新的持久化机制或运行时依赖
- 结构化抽取管道替代现有 `device-extraction.ts` 的单次 `generateText` + 手写 JSON parse，用 `generateObject`（ai-sdk structured output）+ Zod schema 约束生成层，多阶段管道提升准确性，对不支持 structured output 的 provider 保留 `generateText` fallback

### 非目标

- 不改变 DeviceSpec / SignalSpec / CapabilitySpec 的数据结构
- 不改变资产持久化路径（YAML 文件 + 版本历史）
- 不扩展 `CapabilityImpl` 的编码表达能力（独立 ADR，见"未解决的问题"）
- 不改变"资产"区域的连接管理功能（ConnectionStudio 不受影响）
- 不引入 copilot 原生文件上传能力（PDF / ESI 通过 copilot 输入区的附件按钮选择文件，读取后注入对话上下文）

---

## 需求与约束

### 硬性需求

1. copilot 可通过工具完成设备建模全生命周期：创建 → 编辑信号/告警 → 校验 → 生成能力 → 保存
2. `DeviceSpec::validate()` 必须覆盖信号 ID 唯一性、量程合法性、协议与 source 类型一致性、scale 表达式语法
3. AI 不得为寄存器地址、量程范围、报警阈值等安全相关字段编造数值——系统提示必须包含此红线
4. 能力生成工具对不支持自动生成的信号返回结构化建议（而非报错），让 AI 接手
5. 现有 `parse_device_yaml_validated` 必须补实
6. 现有设备建模 UI（DeviceImportDrawer、DeviceModelingPanel 编辑能力、CapabilitiesTab 生成按钮）在本 RFC 完成后移除

### 约束

- 新工具遵循现有 `dispatch_query_tool` 的 match 分发模式
- 资产操作工具复用现有 IPC 命令（`save_device_asset` / `add_device_signal` 等），copilot 只是新增调度层
- 新增校验逻辑放在 `crates/dsl-core/`（Ring 1 纯数据层），不引入运行时依赖
- 系统提示变更限定在 `copilot.ts`

## 设计

### 整体架构

```

  ├─ 资产读取工具（Rust IPC，只读，已有）

  │   ├─ search_capabilities           已有
  │   └─ read_asset_yaml               已有
  │
  ├─ 资产操作工具（Rust IPC，写入，新增）
  │   ├─ save_device_asset             新增
  │   ├─ delete_device_asset           新增
```

### 典型对话流程

#### 流程 A：从零建模新设备

```
用户: 帮我建模一台 Modbus TCP 温湿度传感器，型号 SHT-40
AI:   [调用 get_signal_schema_template(protocol: "modbus-tcp")]
AI:   收到。SHT-40 温湿度传感器用 Modbus TCP 通信。
      我需要以下信息来完善信号定义：
      1. 温度寄存器地址？
      2. 湿度寄存器地址？
      3. 温度量程（℃）和湿度量程（%RH）？
      4. 数据类型（默认 float32）？
用户: 温度 40001，湿度 40003，量程 -40~125℃ / 0~100%RH
AI:   [生成 DeviceSpec YAML]
      [调用 validate_device_yaml]
      [校验通过]
      [调用 infer_capabilities_from_signals → 湿度/温度是只读信号，无写信号，返回空能力]
AI:   校验通过。设备建模摘要：
      | 信号 | 类型 | 单位 | 量程 | 寄存器 |
      |------|------|------|------|--------|
      | temperature | analog_input | ℃ | -40~125 | 40001 |
      | humidity | analog_input | %RH | 0~100 | 40003 |
      
      无写信号，不生成能力。
      设备 ID 建议为 `sht40_sensor`，保存？
用户: 保存，ID 用 sht40_01
AI:   [调用 save_device_asset]
AI:   设备 `sht40_01` 已保存。
```

#### 流程 B：修改已有设备

```
用户: 给 sht40_01 加一个报警，温度超过 80℃ 时 critical
AI:   [调用 read_asset_yaml(asset_type: "device", asset_id: "sht40_01")]
      [调用 patch_device_field 追加 alarm]
AI:   已为 `sht40_01` 添加告警：over_temperature（condition: temperature > 80, severity: critical）。
```

#### 流程 C：从 PDF 文件导入建模

```
用户: [点击 copilot 输入框附件按钮 → 选择 SHT-40.pdf]
      [输入框左上角出现附件 chip："SHT-40.pdf ×"]
      [输入文字]：这是设备的说明书，帮我建模
      [点击发送]
AI:   [发送时，PDF 经 extract_text_from_pdf IPC 提取文本]

AI:   从说明书中提取到以下设备信息：
      - 型号：SHT-40 温湿度传感器
      - 协议：Modbus TCP
      - 温度寄存器：40001，湿度寄存器：40003
      
      量程信息不全，请确认：
      1. 温度量程是 -40~125℃ 还是其他？
      2. 湿度量程是 0~100%RH？
用户: 对的
AI:   [生成 DeviceSpec YAML]
      [调用 validate_device_yaml → 通过]
      [调用 save_device_asset]
      [调用 infer_capabilities_from_signals]
AI:   设备 `sht40_sensor` 已保存。无写信号，不生成能力。
```


### A. 校验工具

#### A1. `validate_device_yaml`

实时校验设备 YAML，补实 `parse_device_yaml_validated`。

```typescript
// 入参
{ yaml: string }
// 返回
{
  valid: boolean;
  parsed?: { id: string; device_type: string; signal_count: number; alarm_count: number };
  errors: Array<{ path: string; message: string }>;
  warnings: Array<{ path: string; message: string }>;
}
```

**Rust 侧**：

1. `parse_device_yaml(yaml)` → serde 反序列化
2. 调用新增 `DeviceSpec::validate() -> ValidationResult`
3. 返回 errors（阻断性）+ warnings（不阻断）

**`DeviceSpec::validate()` 校验规则**：

| 规则 | 级别 | 路径 |
|------|------|------|
| 信号 ID 在设备内唯一 | error | `signals[1].id` |
| 信号 ID 非空且符合 `^[a-zA-Z_][a-zA-Z0-9_]*$` | error | `signals[0].id` |
| `range.min < range.max` | error | `signals[0].range` |
| 模拟信号有 `unit` 和 `range` | warning | `signals[0].unit` |
| `source.type` 与 `connection.type` 协议一致 | warning | `signals[0].source` |
| `scale` 表达式括号匹配 | error | `signals[0].scale` |
| `scale` 不含除法（除零风险） | warning | `signals[0].scale` |
| 写信号建议配套 alarm | warning | `signals[2]` |
| 告警 ID 唯一 | error | `alarms[0].id` |
| 告警 condition 非空且括号匹配 | error | `alarms[0].condition` |

**涉及**：`crates/dsl-core/src/device.rs`（`ValidationLevel` / `ValidationDiagnostic` / `ValidationResult` + `DeviceSpec::validate()`）、`crates/dsl-core/src/parser.rs`（补实 `parse_device_yaml_validated`）、`copilot_tools.rs`（match arm）、`copilot-tools.ts`（工具定义）

#### A2. `get_signal_schema_template`

为 AI 提供指定协议的信号源字段约束，避免编造字段或枚举值。

```typescript
// 入参
{ protocol: "modbus-tcp" | "modbus-rtu" | "mqtt" | "serial" | "can" | "can-fd" | "ethercat" }
// 返回
{
  protocol: string;
  source_variants: Array<{
    type: string;           // "register" | "topic" | ...
    description: string;
    fields: Array<{
      name: string;
      type: string;
      required: boolean;
      description: string;
      enum_values?: string[];
      default?: string;
    }>;
  }>;
  signal_types: string[];
  data_types: string[];
  example_signal_yaml: string;
}
```

**Rust 侧**：新函数 `signal_schema_template(protocol: &str) -> Result<serde_json::Value, String>`，硬编码各协议的 `SignalSource` 变体字段元数据。

**涉及**：`crates/dsl-core/src/device.rs`、`copilot_tools.rs`、`copilot-tools.ts`

#### A3. `infer_capabilities_from_signals`

从设备信号推断能力列表，对无法自动生成的信号返回结构化建议。

```typescript
// 入参
{ device_yaml: string; signal_ids?: string[] }
// 返回
{
  capabilities: Array<{ yaml: string; source_signal_id: string; auto_generated: boolean }>;
  unsupported: Array<{
    signal_id: string;
    reason: string;
    suggestion: { source_type: string; encoding_info: Record<string, unknown> };
  }>;
}
```

**Rust 侧**：

1. `parse_device_yaml` → 按 `signal_ids` 过滤写信号
2. Topic / SerialCommand：`build_capability_from_signal()` 自动生成
3. Register / CanFrame / EthercatPdo：返回 `unsupported` + 编码上下文
4. 新增 `CapabilityInference` 枚举，重构单信号级推断

**涉及**：`crates/dsl-core/src/capability.rs`（`CapabilityInference` + 拆分推断函数）、`copilot_tools.rs`、`copilot-tools.ts`

### B. 资产操作工具

新增 8 个 copilot 工具，**封装现有 IPC 命令**。copilot 只增加调度层，不新增 Rust 逻辑。

工具名 | 封装的 IPC | 入参 | 用途
---|---|---|---
`save_device_asset` | `save_device_asset` | `{ id, device_type, spec_yaml }` | 保存/更新设备 YAML
`delete_device_asset` | `delete_device_asset` | `{ asset_id }` | 删除设备
`save_capability_asset` | `save_capability` | `{ id, device_id, spec_yaml }` | 保存/更新能力 YAML
`add_device_signal` | `add_device_signal` | `{ asset_id, signal_yaml }` | 追加信号
`remove_device_signal` | `remove_device_signal` | `{ asset_id, signal_index }` | 删除信号
`bind_device_connection` | `bind_device_connection` | `{ asset_id, connection_type, connection_id, unit? }` | 绑定/解绑连接
`patch_device_field` | `patch_device_field` | `{ asset_id, path, value }` | 修改任意字段

**前端实现**：在 `copilot-tools.ts` 中，这些工具的 `execute` 回调直接调用 `invoke()` 封装的 IPC（与 `dispatchQueryTool` 模式相同），但走独立的 `dispatchDeviceAction` helper 以区分读写。Rust 侧的 `dispatch_query_tool` 增加 match arm 直接调用现有命令实现。

**设计要点**：

- 工具描述中明确标注"此操作会立即持久化到磁盘"，让 AI 在调用前输出确认摘要
- `save_device_asset` 内部先调用 `validate_device_yaml`（双保险），校验失败则拒绝保存
- 不新增 `add_device_alarm` / `remove_device_alarm`——告警通过 `patch_device_field` 追加到 alarms 数组即可，减少工具数量

### C. 系统提示

替换 `copilot.ts` 中 `TOOL_BEHAVIORAL_PROMPT` 内的工作流创建段落为**设备建模优先**模式，或新增条件段落：

```markdown
## 设备建模专家模式

当用户描述设备特征、请求建模/修改设备、或从文档抽取设备时，切换到设备建模专家模式。

### 建模工作流

1. 理解用户的设备描述（文本粘贴、自然语言描述、或已有设备修改）
2. 调用 `get_signal_schema_template` 获取协议约束
3. 对每个信号，识别缺失的关键字段（寄存器地址、量程、数据类型）
4. 向用户追问缺失信息（最多 3 轮），无法确认的字段标记为 `待确认`
5. 生成 DeviceSpec YAML，调用 `validate_device_yaml` 校验
6. 校验通过后，调用 `save_device_asset` 保存
7. 调用 `infer_capabilities_from_signals` 生成能力建议
8. 自动生成的能力直接调用 `save_capability_asset` 保存
9. 无法自动生成的信号，生成手动 CapabilitySpec proposal，用户确认后保存

### 修改已有设备

1. `search_devices` → `read_asset_yaml` 获取当前状态
2. 与用户确认修改内容
3. `patch_device_field` / `add_device_signal` / `remove_device_signal` 执行修改
4. `validate_device_yaml` 校验修改后的完整性

### 红线

- **绝不为安全相关字段编造数值**：寄存器地址、量程范围、报警阈值、CAN ID、EtherCAT PDO 索引等，用户没有提供则必须追问或标记为待确认
- 协议字段必须与 connection.type 一致
- 模拟信号必须声明量程和单位
- 写信号建议配套 alarm
- 保存前必须调用 validate_device_yaml 校验

### 输出格式

建模完成后输出结构化摘要：
1. 设备基本信息（ID、类型、连接）
2. 信号表（ID、类型、单位、量程、数据源）
3. 校验结果（错误/警告）
4. 已保存的能力列表
5. 需要人工确认的能力列表（附原因）
6. 待确认字段清单（如有）
```

### D. `DeviceSpec::validate()` 类型设计

```rust
/// 校验诊断级别。
#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
pub enum ValidationLevel {
    Error,
    Warning,
}

/// 单条校验诊断。
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ValidationDiagnostic {
    pub level: ValidationLevel,
    pub path: String,
    pub message: String,
}

/// 校验结果。
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ValidationResult {
    pub diagnostics: Vec<ValidationDiagnostic>,
}

impl ValidationResult {
    pub fn is_valid(&self) -> bool {
        self.diagnostics.iter().all(|d| d.level != ValidationLevel::Error)
    }
}
```

### F. 资产操作工具的 dispatch 扩展

现有 `dispatch_query_tool` 仅处理只读查询。资产操作工具需要访问与现有设备命令相同的 Tauri state（AppHandle + workspace_path）。


#### 发送时的处理流程

1. 用户点击发送
2. 如果有附件：
   - **PDF**：读取文件为 base64 → `extract_text_from_pdf` IPC → 返回原始文本 → **经多阶段抽取管道处理**（见 §H）→ 结构化结果注入对话

3. 将处理结果拼接到用户消息前，构造增强的 user message
4. 将增强后的消息传入 `copilotStream()` 的 messages 数组
5. 清除附件状态
6. 对话历史中保留增强后的完整消息（文件内容不再二次处理）

- copilot 面板组件（持有附件状态 + 附件栏 + 附件按钮渲染）
- `copilot-stream.ts`（`copilotChatStream` 函数签名增加可选 `attachment` 参数，发送前处理 IPC 调用和消息拼接）
- 新增 `web/src/components/copilot/CopilotAttachment.tsx`（附件 chip 组件）

#### 设计要点

- 文件内容**不**存入 copilot 会话持久化（SQLite）——只存在于当轮对话的 messages 数组中。重新加载历史对话时，附件内容已在消息文本中，不需要再次读取文件

### H. 结构化抽取管道

替代现有 `device-extraction.ts` 的单次 `generateText` + `extractJsonFromResponse` 脆弱解析。用于 PDF 附件发送时的预处理阶段——将原始说明书文本转化为结构化设备模型骨架，再注入 copilot 对话由 AI 追问补全。

#### 问题

现有 `device-extraction.ts` 的抽取路径：

```
generateText(PROMPT) → extractJsonFromResponse(text) → JSON.parse(raw)
  → 失败则 buildCorrectionPrompt → 再试一次
```

问题：
1. **脆弱解析**：`extractJsonFromResponse` 用正则剥 markdown 代码块，模型输出格式稍有偏差就崩溃
2. **单次抽取**：一次 `generateText` 要求模型同时完成大纲识别、信号填充、能力推断——信息密度过高，遗漏率高
3. **无 schema 约束**：模型生成 JSON 的字段名/类型/枚举值无运行时校验，错误推迟到 Rust serde 层才发现
4. **修正循环粗糙**：失败后重新 prompt 整体重试，不针对具体错误字段

#### 设计：四阶段管道

```
PDF 原始文本
  │
  ▼
Stage 1：大纲抽取（generateObject + Zod）
  │  → DeviceOutline { id, type, manufacturer?, model?, protocol?, signalCount, connection? }
  │
  ▼
Stage 2：信号填充（generateObject + Zod）
  │  → 输入：原始文本 + Stage 1 大纲
  │  → SignalOutline[] { id, signalType, unit?, range?, source:{type, register?, topic?, ...} }
  │
  ▼
Stage 3：Rust 侧校验（validate_device_yaml IPC）
  │  → 输入：Stage 1 + Stage 2 组装为完整 DeviceSpec YAML
  │  → 输出：ValidationResult { errors, warnings }
  │
  ▼
Stage 4：自动修正循环（最多 2 轮）
  │  → 有 errors 时：将 errors 反馈给 generateObject 修正
  │  → 修正后重新 Stage 3 校验
  │  → 2 轮后仍有 errors → 将 errors + 当前 YAML 注入 copilot 对话，由 AI 接手
  │
  ▼
结构化结果注入 copilot 对话
```

#### Provider 兼容性：`generateObject` 与 fallback

```typescript
import { generateObject, generateText } from 'ai';

async function extractWithSchema<T>(
  prompt: string,
  schema: z.ZodSchema<T>,
  provider: AiProviderView,
): Promise<T> {
  const model = await createLanguageModel({ provider });

  // 优先使用 generateObject（structured output）
  // ai-sdk 内部检测 provider 能力：支持则走 native structured output，
  // 不支持则走 tool-call 模拟（仍比手写 parse 可靠）
  try {
    const result = await generateObject({ model, schema, prompt, temperature: 0.1 });
    return result.object;
  } catch (structuredError) {
    // fallback：generateText + JSON.parse + schema.safeParse
    console.warn('generateObject 失败，fallback 到 generateText', structuredError);
    const textResult = await generateText({ model, prompt, temperature: 0.1, maxOutputTokens: 16384 });
    const jsonText = extractJsonFromResponse(textResult.text);
    const parsed = JSON.parse(jsonText);
    return schema.parse(parsed);
  }
}
```

**fallback 策略**：
- `generateObject` 内部已处理大部分 provider 兼容性（通过 tool-call 模拟 structured output）
- 仅在 `generateObject` 完全失败时（如 provider 不支持 tool calling），fallback 到 `generateText` + `JSON.parse` + `schema.parse`（Zod 校验仍在 fallback 路径生效）
- Zod schema 的 `.parse()` 在两条路径都提供类型安全——fallback 不是退回到无校验

## 备选方案考虑

### 方案 A：copilot 全量接管 + 移除现有建模 UI（本提案）

copilot 成为设备建模唯一入口，新增校验工具 + 资产操作工具 + 专家系统提示。移除 DeviceImportDrawer 和 DeviceModelingPanel 编辑能力。

- **优势**：消除入口碎片化——一条路径完成全部建模；AI 追问补全信息；实时校验；渐进式能力生成；"资产"区域 UI 大幅简化（只读 + 文件拾取）
- **劣势**：系统提示膨胀（~60 行设备建模段落）；依赖 AI 编排能力；资产操作通过工具暴露（安全面扩大）；copilot 附件 UI 需要新组件和文件处理逻辑

### 方案 B：前端专用设备建模向导 UI

新增独立的分步式设备建模页面。

- **优势**：用户体验可控；字段补全即时反馈
- **劣势**：新组件工作量大；步骤式表单对复杂设备不灵活；无法利用 AI 语义理解；不解决入口碎片化（反而新增一个入口）

### 方案 C：只加校验工具，不加资产操作工具

在 copilot 中只加 `validate_device_yaml` / `get_signal_schema_template` / `infer_capabilities_from_signals`，用户确认后需自行到现有 UI 保存。

- **优势**：最小变更；安全面不扩大
- **劣势**：copilot 仍是旁观者，不是主入口；用户仍需在 copilot 和设备编辑器间跳转；没有解决碎片化问题

### 方案 D：将 DeviceImportDrawer 改造为 copilot 嵌入式面板

在 DeviceImportDrawer 内嵌 copilot 对话，设备建模上下文限定在 drawer 内。

- **优势**：上下文明确；不污染通用 copilot 对话
- **劣势**：两个 copilot 实例增加维护成本；与 RFC-0005 的"单一 copilot 面板"路线不一致；drawer 空间有限

**推荐方案 A**。理由：UI 并存违反单一真值源原则——两条建模路径必然产生状态不同步和用户困惑。方案 C 不解决碎片化。方案 B/D 新增 UI 复杂度但收益不如方案 A。移除现有 UI 是清理技术债的机会。

---

## 缺点与风险

1. **系统提示膨胀**：设备建模专家段落约 60 行 + 11 个新工具的 description。缓解：Phase 1 仅注入校验工具 + 最小系统提示，验证 AI 编排能力后再加资产操作工具
2. **AI 编排失败**：弱模型可能跳过校验、不追问缺失字段、调用错误工具。缓解：工具 description 明确调用顺序；`save_device_asset` 内部强制 validate（双保险）；系统提示红线条款
3. **资产操作安全面**：copilot 现在能直接写入/删除设备资产。缓解：工具描述注明"立即持久化"；系统提示要求保存前输出确认摘要；未来可加用户确认门控（工具返回 pending → 用户点击确认 → 执行）
4. **`CapabilityImpl` 表达力不足**：CAN / Modbus / EtherCAT 写信号的自动生成仍不可能。本 RFC 以"返回结构化建议 + AI 辅助手动建模"作为过渡方案。根本解决需扩展 `CapabilityImpl`（独立 ADR）
5. **UI 移除的回退风险**：移除 DeviceImportDrawer 和手动编辑表单后，如果 copilot 编排失败（AI 模型不可用、网络问题），用户无法建模设备。缓解：保留 Rust 侧 IPC 命令不动——紧急情况下可临时恢复前端表单；ESI 导入是确定性路径（不依赖 AI），通过附件按钮仍可用
6. **附件 UI 的文件大小和 token 限制**：大 PDF 提取的文本可能超出 AI 上下文窗口。缓解：多阶段管道在 Stage 1/2 已将原始文本压缩为结构化数据，注入 copilot 的是摘要而非全文；Stage 1/2 的 `generateObject` 调用仍需处理完整文本，超长时截断到 30k 字符
7. **`generateObject` provider 兼容性**：部分国产模型不支持 structured output / tool calling，`generateObject` 可能失败或产出低质量结果。缓解：fallback 到 `generateText` + Zod `schema.parse`（Zod 校验在两条路径都生效）；Phase 5 需要测试所有已配置 provider 的兼容性

## 未解决的问题

1. **`CapabilityImpl` 编码表达力扩展**：当前 `ModbusWrite` / `CanWrite` 只能表达模板字符串，丢失编码语义。是否需要扩展？本 RFC 以"返回结构化建议 + AI 辅助"作为过渡。根本解决需要独立 ADR
2. **系统提示条件注入**：设备建模专家段落是否按对话上下文动态注入？始终注入更简单但增加 token 开销；动态注入需要额外的意图分类逻辑
3. **资产操作的用户确认门控**：当前设计是 AI 调用工具直接执行。是否需要在 copilot UI 层增加确认按钮（AI 输出"将保存设备 xxx"，用户点击确认后才执行）？这需要扩展工具协议（返回 pending → 用户确认 → 二次调用），Phase 1 先不做
4. **`ValidationDiagnostic` 的复用范围**：是否应上提到 `crates/core/` 以便 `ConnectionSpec::validate()` 等也统一使用？当前放在 `dsl-core`，后续需要时可上提
5. **大 PDF 的上下文窗口策略**：多阶段管道已将原始文本压缩为结构化摘要，但 Stage 1/2 的 `generateObject` 调用仍需处理完整 PDF 文本。超长文本（>50k 字符）是否需要在 Stage 1 前增加预处理步骤（按段落/页码分片、先摘要再抽取）？
6. **`generateObject` 的 provider 兼容性矩阵**：ai-sdk 的 `generateObject` 对不同 provider 的支持程度不同（OpenAI 原生支持、部分国产模型通过 tool-call 模拟、极少数不支持）。需要在 Phase 5 测试所有已配置 provider 的兼容性，确认 fallback 路径的触发条件和可靠性
7. **设备详情只读视图的交互**：移除编辑能力后，用户在只读详情中看到错误信息时，是否需要"在 copilot 中修复"按钮（将设备 ID 注入 copilot 对话作为上下文）？这是一个便利性增强，Phase 6 可选
8. **附件 UI 的多文件支持**：当前设计一次只允许一个附件。ESI 导入可能同时需要多个从站文件。是否需要支持多附件？Phase 6 先实现单附件，后续按需扩展
9. **管道 Stage 数量的 tradeoff**：四阶段管道增加了 AI 调用次数（至少 2 次 `generateObject` + 1 次 `validate_device_yaml` IPC + 可能的修正循环）。对于简单设备（1-2 个信号）可能过度。是否需要根据 Stage 1 的 `signalCount` 动态跳过 Stage 2（简单设备合并为一次抽取）？
