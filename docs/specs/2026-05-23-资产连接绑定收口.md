# 资产连接绑定收口 Design

**日期**：2026-05-23

**状态**：设计草案

## 背景

当前连接资产已经从旧 `connections.json` 收敛到 `dsl/connections/*.connection.yaml`，设备与能力资产也都进入 DSL 资产体系。这个方向是对的，但产品链路仍然把“连接资源”、“设备语义”和“节点执行”暴露成多个可重复配置点：

```text
新建设备
  -> 新建连接
  -> 在连接中配置现场参数
  -> 在设备上绑定连接
  -> 在节点上再次绑定连接
  -> 部署
```

EtherCAT 场景最明显：用户导入 ESI/ENI 后，还要新建 EtherCAT 连接、选网卡、把设备绑定到连接、再在 PDO 读写或信号节点里选择同一条连接。类似问题也存在于 Modbus、Serial、CAN、MQTT、HTTP/Bark 等协议。根因不是某个协议的 UI 太复杂，而是 Nazh 缺少一条跨协议的绑定规则：

- 哪一层拥有连接配置。
- 哪一层拥有设备语义。
- 哪一层负责从设备/能力继承连接。
- 哪些节点允许直接绑定连接。
- 部署时应该解析全部连接资产，还是只解析实际引用的连接。

当前代码事实：

- `ConnectionSpec` 是工程资产，描述协议拓扑、治理策略、密钥引用，不保存运行态状态。
- `DeviceSpec.connection` 已经能保存设备到连接的引用。
- Workflow DSL 编译 `capabilityCall` 时会从设备连接派生 `connection_id`。
- `deviceSignalRead` / `capabilityCall` 运行时仍需要 `connection_id`，低层协议节点也直接暴露 `connectionId`。
- `deploy_workflow` 目前从工作区解析连接资产并注册到 `ConnectionManager`，真实硬件/网络会话通常在节点 `on_deploy` 或 `transform` 中借用连接后建立。

## 目标

- 建立跨协议一致的资产绑定模型，避免用户在设备、连接、节点三处重复选择同一连接。
- 让业务编排主路径只操作设备信号和设备能力，而不是协议连接。
- 保留低层协议节点作为调试、适配器和兼容入口，但让它们从产品主路径降级。
- 在资产阶段提供显式诊断能力，让连接错误尽早暴露，而不是只能等部署或首次运行。
- 部署时只解析当前工作流实际引用的连接资产，避免无关坏连接阻塞部署。
- 保持 `ConnectionManager` 的运行态边界：只负责定义注册、治理、RAII 借出、共享会话和健康状态，不读取工程文件，不保存设备语义。

非目标：

- 本文不决定新的协议驱动实现。
- 本文不引入连接热切换。连接资产或设备绑定变化后，仍以重新部署为主路径。
- 本文不要求删除所有低层协议节点，只规定它们不应是 AI 编排和普通业务画布的首选路径。

## 核心原则

### 绑定只做一次

一个业务设备应在设备资产上绑定默认连接。业务节点引用设备信号或能力时继承这个绑定，不再要求用户重复选择连接。

```text
ConnectionAsset: "这条通道怎么连"
DeviceAsset: "这台设备挂在哪条通道上"
CapabilityAsset: "这台设备能做什么"
WorkflowNode: "调用哪个设备信号或能力"
```

### 连接是资源，不是业务主语

连接资产表达物理或协议资源，例如串口、Modbus TCP endpoint、MQTT broker/topic 根、CAN/SLCAN 通道、EtherCAT master 网卡、HTTP endpoint。它不表达“压力机”、“伺服轴”、“温控器”这类业务设备。

业务工作流的主语应是 Device / Capability。普通用户和 AI 编排都应优先生成：

- `deviceSignalRead`
- `deviceEventTrigger`
- `capabilityCall`
- 未来的高级设备动作节点

低层节点只用于调试、迁移和适配：

- `modbusRead`
- `serialTrigger`
- `mqttClient`
- `canRead`
- `canWrite`
- `ethercatPdoRead`
- `ethercatPdoWrite`
- HTTP/Bark 等协议工具节点

### 隐式继承必须显式可见

节点从设备继承连接不等于静默 fallback。UI、编译产物和部署审计必须能看到解析后的连接来源：

```text
deviceSignalRead(press_1.pressure)
  resolved_connection: press_modbus
  source: device.connection
```

如果找不到连接，必须 fail fast，并指出缺失的是设备绑定、连接资产、secret，还是环境覆盖。

### 资产保存不建立持久连接

保存连接资产或设备资产时，不应持有真实硬件/网络会话。真实会话属于部署期和运行期资源，由 `ConnectionManager` / `ConnectionGuard` 管理。

资产页需要显式“测试/诊断”动作，但诊断是一次性 probe：

```text
加载单个连接资产
  + 当前环境覆盖
  + 本机 secret
  -> 创建临时运行时定义
  -> 协议级最小握手或只读探测
  -> 立即释放
  -> 返回结构化诊断
```

## 目标绑定模型

### ConnectionAsset

职责：

- 保存协议拓扑和治理策略。
- 保存 secret 引用，不保存明文 secret。
- 保存本机可覆盖字段的工程默认值，例如 host、port、网卡名、串口路径、broker 地址。
- 提供协议级诊断入口。

不职责：

- 不保存设备语义。
- 不保存运行态健康。
- 不因为资产被打开或保存而建立持久连接。

示例：

```yaml
id: line1_ethercat
protocol:
  type: ethercat
  backend: soem
  interface: en5
  cycle_time_ms: 1
  op_timeout_ms: 2000
  dc_sync0_period_us: 1000
  dc_sync0_shift_us: 0
  dc_start_delay_us: 100000
governance:
  connect_timeout_ms: 3000
  operation_timeout_ms: 2000
  heartbeat_interval_ms: 1000
  heartbeat_timeout_ms: 500
  rate_limit_max_attempts: 5
  rate_limit_window_ms: 10000
  rate_limit_cooldown_ms: 30000
  circuit_failure_threshold: 3
  circuit_open_ms: 60000
  reconnect_base_ms: 500
  reconnect_max_ms: 5000
```

### DeviceAsset

职责：

- 保存设备身份、信号、告警、协议语义和默认连接引用。
- 对共享总线设备保存总线内定位信息，例如 Modbus unit、CAN node id、EtherCAT slave address / position。
- 成为业务节点继承连接的默认来源。

不职责：

- 不保存连接密钥。
- 不重复保存完整连接参数。
- 不承担连接治理和健康状态。

示例：

```yaml
id: servo_axis_1
type: servo_axis
connection:
  type: ethercat
  id: line1_ethercat
ethercat_identity:
  slave_address: 1001
  product_code: 123456
signals:
  - id: position_actual
    signal_type: analog_input
    unit: mm
    source:
      type: ethercat_pdo
      slave_address: 1001
      pdo_index: 24576
      entry_index: 24640
      sub_index: 1
      bit_len: 32
      data_type: i32
```

### CapabilityAsset

职责：

- 声明设备动作和实现方式。
- 引用设备资产。
- 默认继承设备绑定连接。

只有在能力本身确实跨设备、跨通道或使用外部服务时，才允许显式声明连接覆盖。覆盖必须在 UI 中标为高级选项，并在编译和部署审计中记录来源。

### WorkflowNode

业务节点职责：

- 引用设备、信号或能力。
- 展示解析后的连接，但不要求用户手动选择。
- 如果连接继承失败，给出可定位错误和跳转入口。

调试/适配器节点职责：

- 允许直接选择 `connectionId`。
- 明确标记为“协议调试”或“低层适配器”。
- 不应被 AI 编排默认生成，除非用户明确要求底层协议节点。

## 绑定解析规则

解析顺序：

1. 低层调试节点的显式 `node.connection_id`。
2. 高级节点的能力级显式覆盖，默认不开启。
3. 设备资产的 `device.connection.id`。
4. 缺失则拒绝部署或拒绝编译，不自动猜默认连接。

协议类型校验：

- 节点或能力声明所需协议族。
- 解析出的连接资产必须与协议族匹配。
- `modbus-tcp` 与运行时 `modbus` 这类历史别名应在统一映射层处理，不能散落在 UI 和节点代码中。

引用范围：

- 部署时只解析当前工作流实际引用的连接。
- 引用来源包括节点 `connection_id`、设备绑定、能力覆盖、设备事件监听配置。
- 无关连接资产无效不应阻塞当前工作流部署。
- 项目级“全连接检查”作为独立诊断命令，不混入部署硬前置。

解析产物：

```text
WorkflowGraph
  + Device/Capability snapshots
  -> referenced_connection_ids
  -> resolve only those ConnectionSpec files
  -> register resolved definitions into ConnectionManager
  -> deploy nodes
```

部署审计应记录脱敏摘要：

```json
{
  "node_id": "read_position",
  "device_id": "servo_axis_1",
  "connection_id": "line1_ethercat",
  "binding_source": "device.connection",
  "connection_asset_hash": "..."
}
```

## 主路径 UX

### 设备建模入口

目标路径：

```text
上传说明书 / 导入 ESI / 导入点表
  -> 生成或编辑设备资产
  -> 选择已有连接或在同一向导中新建连接
  -> 绑定一次
  -> 运行诊断
  -> 保存设备版本
```

关键要求：

- 如果设备缺连接，设备卡片显示“未绑定连接”，提供“选择连接 / 新建连接”动作。
- 如果连接资产缺失，显示“连接资产不存在”，提供跳转。
- 如果连接存在但诊断失败，显示诊断结果，不阻止保存设备资产，但部署会根据节点语义 fail fast。
- 设备详情页显示连接来源和运行态快照，但不要求用户离开设备页才能完成绑定。

### 连接资源管理入口

目标路径：

```text
新建连接
  -> 填写协议参数和治理策略
  -> 保存资产
  -> 保存 secret / 本机覆盖
  -> 测试连接
  -> 查看被哪些设备/节点引用
```

关键要求：

- 连接页面向资源管理员和调试者，不是业务编排主入口。
- 连接页应显示“绑定设备数”和“低层节点直接引用数”。
- 删除或修改连接前要提示受影响设备和工作流。

### 画布节点入口

业务节点：

```text
添加 deviceSignalRead
  -> 选择设备
  -> 选择信号
  -> 自动显示继承连接
```

```text
添加 capabilityCall
  -> 选择设备能力
  -> 自动显示继承连接
```

低层调试节点：

```text
添加 modbusRead / canRead / ethercatPdoRead
  -> 选择连接
  -> 填写协议级地址
  -> 明确显示“协议调试节点”
```

业务节点设置面板不应把 `connectionId` 放在第一屏。若保留高级覆盖，必须折叠在“高级”里，并显示覆盖风险。

## 协议适配规则

| 协议 | 连接资产保存 | 设备资产保存 | 业务节点是否手填连接 | 诊断动作 |
|------|--------------|--------------|----------------------|----------|
| Modbus TCP | host / port / 治理策略 | unit / register 信号 / scale | 否，继承设备连接 | TCP connect + unit 读测试寄存器 |
| Serial | port_path / baud / frame 参数 | command / delimiter / decode 规则 | 否，继承设备连接 | 打开串口 + 可选请求响应测试 |
| MQTT | broker / port / client_id / auth | topic / payload schema | 否，继承设备连接 | broker connect + subscribe/publish dry-run |
| CAN/SLCAN | channel / baud / bitrate | can_id / byte offset / node id | 否，继承设备连接 | 打开通道 + 可选监听窗口 |
| EtherCAT | backend / interface / cycle / DC 参数 | slave identity / PDO entry | 否，继承设备连接 | 打开 master + scan slaves + PDO 匹配 |
| HTTP | base url / method / headers secret | endpoint 语义或能力模板 | 通常否，能力继承或服务设备继承 | request dry-run 或 HEAD/OPTIONS |
| Bark | server_url / device_key secret | 通知能力语义 | 通常否，能力继承 | 发送测试通知或认证检查 |

## 实施建议

### Phase 1：统一绑定可见性

- 设备详情页和画布节点设置显示“解析后的连接来源”。
- `deviceSignalRead` / `capabilityCall` 的 UI 将连接选择降为只读继承信息。
- 低层协议节点保留连接选择，并统一标识为调试/适配器。
- AI copilot prompt 禁止为高级设备节点直接编造连接 ID，只能选择设备/能力。

### Phase 2：部署只解析引用连接

- 新增引用收集器，从 `WorkflowGraph`、设备快照、能力快照收集 `connection_id`。
- `resolve_connection_definitions` 支持按 ID 子集解析。
- 部署审计记录 referenced/resolved/skipped 连接数量。
- 无关坏连接不阻塞当前工作流部署。

### Phase 3：资产诊断 IPC

新增协议无关诊断命令，例如：

```text
test_connection_asset(connection_id, workspace_path, environment_id, probe)
test_device_binding(device_id, workspace_path, environment_id, probe)
```

返回结构化结果：

```json
{
  "status": "failed",
  "stage": "probe",
  "connection_id": "line1_ethercat",
  "protocol": "ethercat",
  "message": "未找到 interface en5",
  "recommended_action": "在连接资产或当前环境覆盖中选择正确网卡"
}
```

诊断必须遵守：

- 不把 secret 写入日志、observability、copilot conversation 或 DSL YAML。
- 探测结束后释放资源。
- CAN/EtherCAT 等共享会话必须使用专门的临时 probe 生命周期，不能污染部署期共享会话缓存。

### Phase 4：编译与运行时契约收口

- Workflow DSL 编译高级节点时继续烘焙解析后的 `connection_id`，但记录 `binding_source`。
- 长期可以引入 `BindingResolutionSnapshot`，让节点配置保存设备/能力快照和连接解析摘要，避免只靠裸 `connection_id` 难以解释来源。
- 前端 `connectionDefaults` 只服务低层调试节点，不再给高级设备节点自动填默认连接。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A：所有节点都直接选择连接 | 实现最简单，当前兼容性最好 | 重复绑定，容易冲突，AI 编排要理解协议资源 | 不作为主路径 |
| B：只在设备绑定连接，高级节点继承 | 用户心智清晰，符合设备语义优先，减少重复配置 | 需要补绑定解析和诊断 UI | 推荐 |
| C：连接由设备导入流程自动生成且不可编辑 | 设备建模最短 | 多设备共享连接、现场覆盖和治理策略难处理 | 仅适合向导内快捷创建，不作为底层模型 |
| D：部署期自动猜测默认连接 | 用户操作少 | 违反运行时配置显式声明，错误不可解释 | 拒绝 |

## 测试策略

- Rust：
  - 连接引用收集器覆盖节点显式连接、设备绑定、能力继承、重复引用去重。
  - 部署只解析引用连接，无关坏连接不阻塞。
  - 缺设备绑定、缺连接资产、协议不匹配、缺 secret 都 fail fast 且错误可定位。
- Frontend：
  - 设备详情页绑定一次后，`deviceSignalRead` / `capabilityCall` 设置页显示继承连接。
  - 高级节点默认不展示可编辑连接选择。
  - 低层协议节点仍可直接选择连接，并显示调试/适配器语义。
- E2E：
  - Modbus 设备绑定连接后，从设备信号创建节点并部署。
  - EtherCAT 设备导入后绑定总线连接，节点不再重复选择连接。
  - 工作区存在一个无关坏连接时，不影响只引用另一个连接的工作流部署。
- 文档/生成物：
  - 更新 root `AGENTS.md` 设计原则或 IPC surface。
  - 更新 `crates/dsl-core/AGENTS.md` 的 Device/Connection 修改 checklist。
  - 若新增 IPC 类型，运行 `cargo test -p tauri-bindings --features ts-export export_bindings`。

## 风险

- 风险：隐藏连接选择后，用户不知道节点实际使用哪条连接。
  - 缓解：业务节点必须显示解析后的连接、来源和跳转入口。
- 风险：设备绑定无法覆盖少数跨通道能力。
  - 缓解：保留能力级高级覆盖，但必须显式标记并审计。
- 风险：诊断 probe 与部署共享会话互相污染，尤其是 CAN/EtherCAT。
  - 缓解：诊断使用独立生命周期，结束后清理，不写入部署共享会话缓存。
- 风险：部署只解析引用连接后，项目级坏连接更晚被发现。
  - 缓解：提供“全连接检查”独立入口，不让它成为普通部署硬前置。
- 风险：历史低层节点仍依赖 `connectionId`，短期无法完全隐藏。
  - 缓解：主路径先收口高级设备节点，低层节点通过分类、文案和 AI prompt 降级。
